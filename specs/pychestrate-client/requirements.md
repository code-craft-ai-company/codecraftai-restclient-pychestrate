# Requirements

## Introduction

The `pychestrate-client` feature provides a typed REST client for the
Pychestrate continuous-integration and orchestration service. Like the sibling
GitHub client, it is **generated**: `PychestrateRestClientGenerator` consumes
the OpenAPI 3.1 contract vendored at
`generation/specs/pychestrate.yaml` (Pychestrate Service API, version
`0.0.7-preview`) and emits the top-level client, one API-group module per tag,
and a catalogue of `SchemaObject` model classes.

Two modules are hand-written: `pychestraterestclientbase.py`, which implements
the three Pychestrate security schemes, and
`generation/pychestraterestclientgenerator.py`, which configures the generator.
Everything else carries the `# Auto-generated by RestClientGenerator. DO NOT
EDIT.` banner.

The client is built on `RestClientBase` from `codecraftai-restclient-base` and
takes credentials from `codecraftai-credentials`. Generated methods accept
`aspects: Optional[AspectsRest] = None` so retry, timeout, and logging policy
stay caller-controlled; when omitted the client's construction-time aspects
apply.

## Requirements

### Requirement 1: Authenticate Using the Declared Security Schemes

**User Story:** As a caller, I want the client to select the right Pychestrate
auth scheme from the credential I hand it so that browser sessions, CI API
keys, and pod-agent mTLS all work through one client.

#### Acceptance Criteria

1. WHEN a `PychestrateRestClient` is constructed THE SYSTEM SHALL default the
   `Accept` header to `application/json` without overwriting a caller-supplied
   `Accept`.
2. WHEN the credential exposes a non-empty `api_key` attribute THE SYSTEM SHALL
   send it as the `X-Pychestrate-Api-Key` header, matching the
   `pychestrate_api_key` security scheme.
3. WHEN the credential exposes a non-empty `token` attribute and no `api_key`
   THE SYSTEM SHALL send `Authorization: Bearer <token>`.
4. WHEN the credential exposes both `client_cert` and `client_key` THE SYSTEM
   SHALL configure the `requests.Session` with that certificate pair, matching
   the `pychestrate_mtls` scheme required by the pod-client endpoints.
5. THE SYSTEM SHALL apply the header and certificate paths independently, so a
   credential carrying both an API key and client certificate material
   configures both.
6. THE SYSTEM SHALL build the session in `PychestrateRestClientBase.authenticate`
   and SHALL NOT perform a login round trip; the `pychestrate_session` cookie
   scheme is established out of band by the HTML login form.

### Requirement 2: Cover the Pychestrate API Surface by Tag Group

**User Story:** As a caller, I want the service surface partitioned by domain so
that I can find an endpoint family without reading the OpenAPI contract.

#### Acceptance Criteria

1. THE SYSTEM SHALL expose one `RestApiGroup` subclass per OpenAPI tag that
   owns at least one operation, named `<PascalTag>ApiGroup`, in
   `groups/<tagslug>.py`, reachable as a read-only property on the client.
2. THE SYSTEM SHALL cover the identity and authorization surface through the
   `auth`, `me`, `users`, `rbac`, and `audit` groups.
3. THE SYSTEM SHALL cover the configuration surface through the `secrets`,
   `variables`, `flags`, `tagging`, `retention`, and `notifications` groups.
4. THE SYSTEM SHALL cover the project surface through the `projects` and
   `project_templates` groups, including member add/remove, role removal,
   archive/unarchive, and patch.
5. THE SYSTEM SHALL cover the fleet surface through the `clients`,
   `enrollment`, `agents`, `pods`, and `plugin_api` groups, including
   enrollment-token issue/redeem/revoke and pod definition, registration,
   topology, state-history, and template materialization.
6. THE SYSTEM SHALL cover the execution surface through the `runs`,
   `test_runs`, `test_catalog`, `dispatch`, `progress`, `results`, and
   `artifacts` groups.
7. THE SYSTEM SHALL NOT emit a group for a declared tag that owns no
   operations; the `metrics` tag is declared in the contract as planned and has
   no generated group.

### Requirement 3: Support the Pod-Client Ingestion Path

**User Story:** As a pod client agent, I want acknowledgement, progress, and
result endpoints on the same client so that the agent does not hand-roll HTTP.

#### Acceptance Criteria

1. WHEN the agent calls `dispatch.dispatch_ack_run(...)` THE SYSTEM SHALL POST
   the acknowledgement for the dispatched run.
2. WHEN the agent calls `dispatch.envelope_signing_keys_list(...)` THE SYSTEM
   SHALL return a `Signingkeyset` so envelope signatures can be verified.
3. WHEN the agent calls `progress.progress_post_frame(...)` THE SYSTEM SHALL
   POST the live progress frame.
4. WHEN the agent calls `results.results_post_complete(...)` THE SYSTEM SHALL
   POST the final result manifest.
5. WHEN the agent calls `results.artifacts_presign_upload(...)` THE SYSTEM
   SHALL return an `Artifactpresignresponse` describing the upload target.
6. WHEN the agent calls `clients.clients_dispatches_next(...)` THE SYSTEM SHALL
   return the next `Pendingdispatch` for that client.

### Requirement 4: Type Responses Against a Generated Model Catalogue

**User Story:** As a caller, I want responses returned as typed objects so that
field access is checkable.

#### Acceptance Criteria

1. THE SYSTEM SHALL emit one `SchemaObject` subclass per named schema in
   `components.schemas` under `models/`, with each property declared as a
   `Field(...)` descriptor carrying its type, `required` flag, and description.
2. WHEN an operation's 200 response references a named schema THE SYSTEM SHALL
   return that model type, constructed via `from_dict` — for example
   `runs.runs_get_by_id` returns `Run` and `runs.runs_list` returns `Runpage`.
3. WHEN an operation's 200 response is an inline anonymous object THE SYSTEM
   SHALL type the return as `Dict[str, Any]` and return the decoded JSON; this
   is the case for the `items`-envelope list endpoints such as
   `clients.clients_list` and `projects.projects_list_members`.
4. WHEN an operation declares no resolvable 200 response schema THE SYSTEM
   SHALL type the return as `Any`.
5. WHEN a payload does not fit its declared model THE SYSTEM SHALL return the
   raw dictionary rather than raising, except that `SemanticError` SHALL
   propagate (`RestApiGroup._parse_item`).
6. THE SYSTEM SHALL model the paging envelope as `Pagemeta`, carrying `page`,
   `per_page`, `total`, and an optional `next_cursor`, referenced by the
   typed page models.

### Requirement 5: Generated Method Contract

**User Story:** As a caller, I want every generated method to behave the same
way so that the client is predictable across 97 operations.

#### Acceptance Criteria

1. THE SYSTEM SHALL emit path parameters as positional parameters and compose
   the leaf via `str.format` against a `leaf_template` literal.
2. THE SYSTEM SHALL emit query parameters as keyword-only parameters and SHALL
   omit any left at `None` from the request `params`.
3. THE SYSTEM SHALL emit `exp_status`, `headers`, and `aspects` as keyword-only
   parameters on every generated method.
4. WHEN `exp_status` is not supplied THE SYSTEM SHALL default it to the 2xx
   status codes declared for that operation in the contract.
5. WHEN `aspects` is `None` THE SYSTEM SHALL fall back to `client.aspects`.
6. WHEN a `headers` argument is supplied THE SYSTEM SHALL send it in place of
   the client's default headers, not merged with them.
7. WHEN a response carries status 204 or 205, or status 202 with a zero-length
   body, THE SYSTEM SHALL return `None` without decoding a body.

### Requirement 6: Error Behaviour Delegated to the Base Client

**User Story:** As a caller, I want HTTP failures classified the same way as
every other ccai REST client.

#### Acceptance Criteria

1. THE SYSTEM SHALL route every request through `RestClientBase.perform_call`,
   selecting the execution strategy from `aspects.action_pattern`.
2. WHEN the response status is outside `exp_status` THE SYSTEM SHALL log the
   formatted error and raise the typed exception selected by
   `raise_for_http_status` from `codecraftai-errors`.
3. WHEN a call fails with `HttpForbiddenError` THE SYSTEM SHALL discard the
   session and re-authenticate exactly once before bubbling the failure.
4. THE SYSTEM SHALL generate the contract's RFC 7807 error document as the
   `Problem` model in `models/problem.py`.

### Requirement 7: Regenerate the Client from the Contract

**User Story:** As a maintainer, I want the client rebuilt from a refreshed
contract so that service changes land without hand edits.

#### Acceptance Criteria

1. THE SYSTEM SHALL provide `PychestrateRestClientGenerator` bound to
   `PychestrateRestClientBase`, with module roots rooted at
   `ccai.pychestrate.rest.client`.
2. THE SYSTEM SHALL write model modules into `models/` rather than the base
   generator's default `schemas/` directory.
3. WHEN `generation/specs/pychestrate.yaml` is absent THE SYSTEM SHALL raise
   `FileNotFoundError` naming the expected path and the
   `pychestrate-service/specs/openapi/pychestrate.yaml` source to copy from.
4. THE SYSTEM SHALL make regeneration runnable as `make generate`.
5. THE SYSTEM SHALL leave `pychestraterestclientbase.py` and the generator
   module itself untouched by a regeneration run.

### Requirement 8: Structural Verification Without Live Calls

**User Story:** As a maintainer, I want the generated shape verified against the
contract so that a bad regeneration is caught before it ships.

#### Acceptance Criteria

1. THE SYSTEM SHALL provide a test suite that performs no HTTP calls, runnable
   as `make test`.
2. THE SYSTEM SHALL verify that the client exposes `runs`, `clients`, and
   `pods` properties returning `RunsApiGroup`, `ClientsApiGroup`, and
   `PodsApiGroup` respectively.
3. THE SYSTEM SHALL verify that the generated `Run` model's required fields
   exactly match the `required` list of the `Run` schema in the contract.
4. THE SYSTEM SHALL verify that the contract's `RunState` enum retains at least
   the `pending`, `dispatching`, `running`, `completed`, `failed`, and
   `cancelled` values and that `Run.state` exists.
